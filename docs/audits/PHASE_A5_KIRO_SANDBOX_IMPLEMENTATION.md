# Phase A5 — Sandboxed Kiro Implementation Profile (Closeout)

## Objective

Grant a single agent profile (`implement`) the minimum capability to **mutate
files inside a disposable job sandbox**, without ever giving the model write
authority over the host project, a shell, the network, or any credential path.
A5 produces deterministic change evidence for a completed implement job but
**never applies** it (apply/discard is A6). All read-only A4 profiles
(`audit`, `plan`, `review`) remain unchanged.

## Architecture

The `implement` profile reuses the A3 sandbox foundation and the A4 Kiro ACP
backend, adding a writable workspace and a single file-mutation tool:

- **Capability is trusted code policy**, keyed on the profile id only
  (`resolveProfileCapability` in `src/executor/agents/acpDriver.ts`). It is
  **never** inferred from prompt text.
- The per-job agent config is generated by `bridgeAgentConfig(..., { write:true })`
  in `src/executor/agents/kiroBackend.ts` and delivered on the runner's home
  volume under an **unguessable** name (`mcp_impl_<32 hex>`), so a
  workspace-supplied `.kiro/agents/<name>.json` cannot override it.
- The runner is driven purely through the Docker Engine API
  (create → start → wait → logs); the runner-internal `runnerMain.js` speaks
  ACP JSON-RPC to `kiro-cli acp` over local stdio. No `docker` CLI, no
  interactive attach.

### Implement profile capability set

- `tools`: `["read","grep","glob","write"]` — the canonical Kiro Built-in
  Tools `write` name (documented aliases `fs_write`, `fsWrite`).
- `allowedTools`: `["read","grep","glob"]` only.
- `mcpServers: {}`, `includeMcpJson: false`, `hooks: {}`, `resources: []`,
  `model: null`. No shell/terminal, web, MCP, AWS, subagents/delegation,
  hooks, or wildcards.

### Path-scoped write policy

- `toolsSettings.write.allowedPaths`: `["/workspace"]` — paths writable without
  prompting.
- `toolsSettings.write.deniedPaths`: `["/home/runner","/tmp","/run/secrets","/run/control"]`.

### allowedTools policy (why `write` is excluded)

Per the official Kiro Agent Configuration Reference, `allowedTools` pre-approves
a tool **and overrides** any allowable pattern configured in `toolsSettings`.
Placing `write` in `allowedTools` would therefore nullify the `/workspace` path
scoping. `write` is consequently **available** (in `tools`) but **not** globally
pre-approved; its non-interactive permission comes solely from
`toolsSettings.write.allowedPaths`. This mirrors Kiro's own Development Workflow
Agent example (write in `tools`, not in `allowedTools`, scoped via
`toolsSettings`).

### ACP trust policy

- `--trust-tools=read,grep,glob`. `write`/`fsWrite`/`fs_write` are **never** in
  `--trust-tools`. Never `--trust-all-tools`, `-a`, `--yolo`, or `*`.

### Writable /workspace isolation

- The workspace is a **Docker-managed job volume** staged from the trusted
  committed HEAD snapshot, mounted **writable** (`ReadOnly:false`) for
  `implement` only. All read-only profiles keep the A4 read-only mount.
- **No host project RW bind** — the runner never receives host filesystem
  authority (`HostConfig.Binds` is empty).
- **No Docker socket** in the runner.
- Runner runs non-root (`1000:1000`), read-only rootfs, `CapDrop:["ALL"]`,
  `no-new-privileges`, private IPC, isolated `HOME`/`KIRO_HOME`/`XDG_*` under
  `/home/runner` (no personal host Kiro state inherited), `/run/secrets` and
  `/run/control` mounted read-only.

### Network / proxy boundary

- Runner is attached to a job-scoped **internal** Docker network; direct
  Internet is denied. Backend-only egress is provided by an allowlist proxy on
  a separate external network. The proxy holds no key, no project, no socket.

### Tracked-symlink fail-closed policy

- For `implement` staging only, the trusted stager scans the committed HEAD
  with `git ls-files -s` for any **Git mode 120000** (symlink) entry
  (`REJECT_SYMLINKS` guard in `GIT_STAGING_SCRIPT`). If present, staging aborts
  with exit 6 **before** the workspace is materialized and before any provider
  execution, surfaced as `PRECONDITION_FAILED` → `FAILED_PRECONDITION`. This
  applies to **all** tracked symlinks regardless of target. Read-only profiles
  are unaffected (A4 parity).

### Deterministic change detection

- A trusted, hardened, read-only manifest helper walks `/workspace` and emits
  one JSON manifest (`[path,size,sha256]`) — once on the pristine staged
  snapshot (baseline) and once after the runner exits (post). The pure diff
  (`changeDetection.ts`) yields added/modified/deleted, `changedCount`,
  `changedBytes`, and a stable `diffHash`. Evidence is produced by the trusted
  helper, **never** by the agent.

### Result semantics

- **Failed mutation → FAILED_AGENT**: a mutation-kind tool call with a terminal
  failure status (`failed`/`error`/`denied`/`refused`/`rejected`/`cancelled`/
  `aborted`/`timeout`/…) maps to `KiroAgentFailure` → `FAILED_AGENT`, even if
  the ACP turn reached `end_turn`. Determination uses the bounded ACP tool
  status evidence only — **never** assistant prose.
- **Zero-diff semantics**: a run with no changes and no failed mutation is not
  an automatic failure; the change set is recorded as-is and the job may reach
  `COMPLETED`.
- **COMPLETED ≠ APPLIED**: reaching `COMPLETED` never mutates the host project.
  Review/apply/discard is A6-owned; the state machine only allows
  `COMPLETED → APPLIED` via an explicit, separate action.

### A4 read-only preservation

- `audit`, `plan`, `review` keep the exact A4 capability: `tools`
  `[read,grep,glob]`, empty `allowedTools`, no write tool/settings/trust,
  read-only workspace mount, no symlink restriction.
